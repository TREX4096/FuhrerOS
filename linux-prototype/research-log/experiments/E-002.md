# E-002 — first full campaign (main + transition + ablation)

**Directory:** `experiments/E-002-all-20260926-0652/` (summary.md, result.json, graphs, raw/)
**Question:** RQ1–RQ5. Which static policy is best per workload (M5), how close is adaptive
(RQ2), what does monitoring cost (RQ3), and how fast does adaptation react (RQ4)?
**Hypotheses:** H1 (random → SPECIALIZED), H2 (sequential → BATCHED), H3 (adaptive ≈ B3),
H4 (monitoring < 1 % CPU at 1 s).
**Setup:**
- Host: Windows 11 → WSL2 (kernel 6.6.87.2) on a Ryzen 5 7520U with 8 GB.
- VM: QEMU 10.2.1 with KVM (nested); bench VM with 4 vCPU, 4 GB and a 40 GB qcow2 overlay (cache=none).
- Guest: kernel 6.12.111-0-virt.
- Runs: reps=3, 10 s runs, 5 s warm-up, data file 5.9 GB (1.5× RAM), caches dropped.
- Configurations shuffled per rep.
- Policy map: v1 (cpu→BATCHED, seq→BATCHED) for the main and transition suites.

## Results (medians of 3; full tables in summary.md)

| workload | B0 | B1 normal | batched | specialized | B2 adaptive | B2 vs B3 |
|---|---|---|---|---|---|---|
| randread IOPS | 1,070 | 842 | 7,721 | **14,860** | 13,334 | −10 % |
| randwrite IOPS | 11,892 | 8,818 | 9,372 | 11,653 | **12,476** | +7 % |
| seqread MB/s | 78.6 | 90.1 | 95.5 | **775** | 101 | −87 % |
| seqwrite MB/s | 62.0 | 71.4 | 66.2 | **876** | 73.5 | −92 % |
| cpu Mops/s | 1,829 | 1,885 | 828 | 2,074 | 1,854 | −11 % (noise, see below) |
| netlat RTT p50 µs | 23.6 | 22.6 | 22.7 | 22.5 | 23.5 | −4 % |

**A6 decomposition** (relative to B1):
- Kernel knobs alone: random read +10 to +17 %, random write up to +25 %, sequential within noise.
- libfuhrer alone (io_uring + O_DIRECT, knobs at stock): random read +1,359 %, sequential read +760 %, sequential write +856 %.
- **Conclusion: nearly all of the storage gain is the library fast path, not the kernel tunables.**

**Tail latency** (p99 µs; the async figures include queueing inside a 32-deep batch):

| | normal | specialized |
|---|---|---|
| randread | 2,925 | 3,869 |
| randwrite | 605 | 9,767 |
| seqread | 32,242 | 9,243 |

SPECIALIZED trades per-request tail latency for throughput on random I/O. Buffered random
writes return from the page cache, so they look faster per call until writeback.

**Transitions (Graph 3):** adaptive reached the mapped policy 3.0–4.1 s after every phase
change (= hysteresis 3 × 1 s interval), with 4–5 switches per run. Static configs never
switch.

**Monitoring overhead (Graph 4):**

| profiler setting | daemon CPU | cpu benchmark vs off |
|---|---|---|
| 1000 ms | 0.087 % | −2.0 % (inside noise) |
| 100 ms | 0.69 % | −1.2 % |
| 10 ms | 5.1 % | −9.0 % |

**Ablations A5/A7:**
- Time to reach SPECIALIZED in the random phase:

  | setting | reaction time |
  |---|---|
  | hysteresis 1 | 1.0 s |
  | default | 3.0 s |
  | hysteresis 5 | 5.1 s |
  | interval 100 ms | 1.0 s |
  | interval 5000 ms | **never** within a 10 s phase |

- Random-read MB/s tracks reaction time: 57 / 52 / 40 / 31 / 4.6.

## Interpretation

- **H1 supported.** SPECIALIZED is best for random reads.
- **H2 refuted** on this platform. SPECIALIZED (O_DIRECT) beats BATCHED for sequential I/O by
  about 8×. Buffered sequential I/O through the page cache is slow under nested
  virtualisation.
- **H3 partially.** Adaptive is within 10 % of B3 on random read and beats B3 on random
  write, but loses badly on sequential I/O. That is because the v1 map pointed sequential
  I/O to the wrong policy (the adaptation mechanism worked; the map did not).
  → **D-006 revised** (seq→SPECIALIZED, cpu→NORMAL) and validated in E-003.
- **H4 supported** at 1 s (0.09 % CPU). Sampling at 10 ms is too expensive.
- **CPU results are dominated by host noise:** CV up to 94 %. CPU and memory
  benchmarks under "lib-only specialized" dropped 50 %, although they never call libfuhrer,
  which is pure interference. Only effects larger than about 2× are trustworthy in this
  environment.

## Threats to validity
- Nested virtualisation; qcow2 on the WSL2 vhdx; loopback-only network tests.
- n=3.
- **Procedural confound:** the class→policy map in the repository was revised *during*
  the run. The transition-ablation runs (A4/A5/A7) copied `fuhrer.conf` at run time and
  therefore used the **revised** map. Their exact configs are stored in
  `raw/ablation-*.conf`, and `analyze.py` reads the map from those files. The main and
  transition suites used the original map.

**Next experiment:** E-003 — validate the revised map (normal vs specialized vs adaptive on
the storage + cpu workloads, plus the transition suite).
