# E-135 — `stress` (final)

- **Question:** M17 / §35 mixed workload / UI_SUGGESTION §41: does the adaptive scheduler keep the desktop responsive while browser-like, build-like, file and network work run at once?
- **Hypothesis:** Adaptive keeps the interactive probe near low-latency levels without starving the rest.
- **Host:** Linux 6.6.87.2-microsoft-standard-WSL2 x86_64; AMD Ryzen 5 7520U with Radeon Graphics (Windows 11 -> WSL2 -> QEMU; KVM nested inside WSL2 when accel=kvm)
- **Guest:** FuhrerOS, 4 vCPU offered / 1 used, 4096 MB
- **QEMU:** QEMU emulator version 10.2.1 (Debian 1:10.2.1+ds-1ubuntu3.1), accel KVM; virtio-blk, FFS0 raw image, host cache=writeback; virtio-net, QEMU user-mode (slirp)
- **Kernel:** FuhrerOS 0.1.0 (own kernel), commit `389c7f5`, 2026-09-26T18:39:49Z
- **Workload:** deskstress 10 s x 3 repetitions x 4 policies: HTTP client+server, two CPU-bound build-proxy workers, 8 MiB file copy loop, TCP stream, interactive probe; order rotated.
- **Policy / configuration:** `rootfs/etc/bench/stress.sh` (copy in the run directory)
- **Metrics:** probe dispatch/wake latency, per-component throughput, context switches, thread classes
- **Result:** Median of 3 (probe dispatch p50 / p99, µs): B0 19,528 / 28,355; B1 19,447 / 32,736; B2 9 / 245; B3 14 / 3,019. Build-proxy jobs/s (x100): B0 55,441, B1 55,726, B2 19,665, B3 4,209. File copy MB/s: B0 0.20, B1 0.19, B2 6.44, B3 5.51. HTTP requests/s: B0 0.09, B1 0.09, B2 2.09, B3 0.19. TCP stream MB/s: B0 2.06, B1 2.04, B2 38.70, B3 99.24. Context switches/s B3 8,340. No HTTP connection failures in any run. Threads under B3 at mid-run: copy/stream/web IO_BOUND (priority 8), probe INTERACTIVE (4), build workers MIXED (12).
- **Variance:** see CV% columns in [summary.md](../../experiments/E-135-stress-20260926-1839/summary.md)
- **Interpretation:** M17: after F-122 the adaptive policy keeps the median interactive latency at 14 µs (round-robin: 19.5 ms), but its p99 (3.0 ms) is 12x the low-latency policy's, and it trades the CPU-bound build work away: 92 % fewer build jobs than round-robin and 79 % fewer than low-latency, while the TCP stream runs 2.6x faster than under low-latency. Cause, visible in the thread classes: busy streaming threads are classified IO_BOUND (many I/O calls, short bursts) and get priority 8 over the MIXED build workers (12); the IO_BOUND rule does not consider CPU share. On this mix the adaptive scheduler does NOT beat the hand-picked low-latency policy. Media: NOT RUN (no audio/video path); build = CPU proxy (no compiler).
- **Threats:** nested virtualisation (Windows → WSL2 → KVM); one CPU used; few repetitions; synthetic workloads.
- **Next experiment:** Add CPU share to the IO_BOUND rule (a busy streamer is not I/O-bound) and rerun E-129 and this suite.
