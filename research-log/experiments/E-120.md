# E-120 — `ablation` (final)

- **Question:** RQ1/RQ3 and NEW_EXPLANATION §38: which parts of the adaptive scheduler produce its effect, and how sensitive is it to window and hysteresis?
- **Hypothesis:** Latency gains need both profiling and class-based parameters; longer windows / more hysteresis react slower and raise tail latency.
- **Host:** Linux 6.6.87.2-microsoft-standard-WSL2 x86_64; AMD Ryzen 5 7520U with Radeon Graphics (Windows 11 -> WSL2 -> QEMU; KVM nested inside WSL2 when accel=kvm)
- **Guest:** FuhrerOS, 4 vCPU offered / 1 used, 4096 MB
- **QEMU:** QEMU emulator version 10.2.1 (Debian 1:10.2.1+ds-1ubuntu3.1), accel KVM; virtio-blk, FFS0 raw image, host cache=writeback; virtio-net, QEMU user-mode (slirp)
- **Kernel:** FuhrerOS 0.1.0 (own kernel), commit `e942a12-dirty`, 2026-09-26T16:34:28Z
- **Workload:** schedbench mixed scenario, 3 repetitions per variant: A1 priority policy (controller off), A2 adaptive with profiling off, A3 round-robin with profiling on, A4 adaptive, A5 adaptive + adaptive cache (from E-120), A6 window 25/500 ms, A7 hysteresis 1/5.
- **Policy / configuration:** `rootfs/etc/bench/ablation.sh` (copy in the run directory)
- **Metrics:** as for sched
- **Result:** Mixed scenario, median of 3. Dispatch p50 / p99 (µs): A1 controller off 29,058 / 30,051; A2 profiling off 11,205 / 17,062; A3 profiling on, no switching 29,057 / 29,341; A4 adaptive 6 / 56; A5 adaptive + adaptive cache 6 / 71; A6 window 25 ms 6 / 60; A6 window 500 ms 6 / 14,042; A7 hysteresis 1 7 / 77; A7 hysteresis 5 6 / 11,990. Batch jobs/s (x100) 954,234-985,723 in all variants. Policy decision time A3 67,255 ns/s, A4 138,256 ns/s. Profiler total for the whole boot: 8.86 ms.
- **Variance:** see CV% columns in [summary.md](../../experiments/E-120-ablation-20260926-1634/summary.md)
- **Interpretation:** RQ1/RQ3: the latency gain needs both profiling and class-based parameters. Profiling alone (A3) changes nothing; the adaptive policy without profiles (A2, every task UNKNOWN) is in between. The adaptive cache (A5) does not change scheduler metrics in this scenario (random I/O). Reaction speed matters: a 500 ms window or hysteresis 5 raises dispatch p99 about 210-250x, because new threads start UNKNOWN and wait behind CPU workers until classified; 25 ms vs 100 ms windows make no measurable difference. Overhead: the profiler used 8.86 ms in a boot of at least 270 s of benchmarks (< 0.004 % of CPU); policy decisions under A4 cost about 0.14 ms per second (0.014 %). The larger cost is about 9x more context switches than round-robin (visible in E-117), which is not in these numbers.
- **Threats:** nested virtualisation (Windows → WSL2 → KVM); one CPU used; few repetitions; synthetic workloads.
- **Next experiment:** Measure context-switch cost directly; per-class initial placement for new threads.
