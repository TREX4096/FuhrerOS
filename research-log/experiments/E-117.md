# E-117 — `sched` (final)

- **Question:** RQ2/RQ6: does the adaptive scheduler (B3) improve interactive latency against fixed policies (B0 round-robin, B1 priority, B2 low-latency) without hurting batch throughput?
- **Hypothesis:** B3 matches B2 on interactive latency and keeps B0's batch throughput in the mixed scenario.
- **Host:** Linux 6.6.87.2-microsoft-standard-WSL2 x86_64; AMD Ryzen 5 7520U with Radeon Graphics (Windows 11 -> WSL2 -> QEMU; KVM nested inside WSL2 when accel=kvm)
- **Guest:** FuhrerOS, 4 vCPU offered / 1 used, 4096 MB
- **QEMU:** QEMU emulator version 10.2.1 (Debian 1:10.2.1+ds-1ubuntu3.1), accel KVM; virtio-blk, FFS0 raw image, host cache=writeback; virtio-net, QEMU user-mode (slirp)
- **Kernel:** FuhrerOS 0.1.0 (own kernel), commit `e942a12-dirty`, 2026-09-26T16:20:21Z
- **Workload:** schedbench: `mixed` = 3 CPU workers + 1 random-read I/O worker + interactive probe (sleep 10 ms, ~0.2 ms work); `batch` = 4 CPU workers + probe. 10 s per run, policy order rotated per repetition.
- **Policy / configuration:** `rootfs/etc/bench/sched.sh` (copy in the run directory)
- **Metrics:** probe wake-up / dispatch / response latency percentiles, batch jobs/s, I/O ops/s, Jain fairness, context switches/s, scheduler overhead ns/s, kernel-assigned classes
- **Result:** Mixed scenario (median of 5): dispatch p50 B0 29,062 µs, B1 29,062, B2 7, B3 6; dispatch p99 B0 29,820, B1 29,621, B2 104, B3 84 µs; batch jobs/s (x100) B0 960,004, B1 964,124, B2 958,827, B3 948,594; I/O ops/s B0 21, B1 22, B2 509, B3 501; context switches/s B0 188, B3 1,753; policy decision time B0 27,646 ns/s, B3 124,805 ns/s. Batch scenario: dispatch p99 B2 52 µs, B3 142 µs; batch jobs/s 970,108-979,645 for all four.
- **Variance:** see CV% columns in [summary.md](../../experiments/E-117-sched-20260926-1619/summary.md)
- **Interpretation:** RQ2/RQ6: B3 and B2 both cut the probe's dispatch latency by about 3-4 orders of magnitude against B0/B1 and raise I/O throughput about 24x, for at most about 1.2 % less batch throughput (B3 vs B0 in the mixed scenario; B1 has CV 11 %). B3 does NOT clearly beat the hand-picked B2: p99 84 vs 104 µs in the mixed scenario but 142 vs 52 µs in the batch scenario, with CV 38-62 %. The adaptive policy's value is that it reaches B2-level behaviour without being told the workload, not that it beats the best fixed policy. Wake latency p50 (979 µs vs 30 ms) contains the tick-phase offset of this boot (F-117).
- **Threats:** nested virtualisation (Windows → WSL2 → KVM); one CPU used; few repetitions; synthetic workloads.
- **Next experiment:** Real desktop traces instead of synthetic workers; more repetitions to separate B2 and B3 tails.
